File I/O

Data That Outlasts The Program

  • Variables disappear when the program ends.
  • Files let a program save data, load it later, and share it with other programs.

Slides 4-36

Files As Streams

  • cin reads from the keyboard.
  • cout writes to the terminal.
  • File streams use the same idea, but the stream is connected to a file.

The operators are familiar: >> extracts data, and << inserts data.

The File I/O Process

  1. Include <fstream>.
  2. Declare a file stream object.
  3. Open the file.
  4. Check that the open worked.
  5. Read or write data.
  6. Close the file.

Every file program follows this pattern.

The fstream Library

Type Direction Common Use
ifstream input read from a file
ofstream output write to a file
fstream input and output read and write with one stream

Use the narrowest stream type that matches the job.

Writing To A File

#include <fstream>
#include <iostream>
using namespace std;

int main() {
    ofstream outFile("scores.txt");

    outFile << "Alice " << 95 << endl;
    outFile << "Bob " << 87 << endl;

    outFile.close();
    return 0;
}

By default, ofstream creates the file if it does not exist and overwrites it if it already exists.

Checking That A File Opened

ifstream inFile("scores.txt");

if (!inFile.is_open()) {
    cerr << "Error: could not open scores.txt" << endl;
    return 1;
}

File code should check the stream before trusting it.

Coding Task

Write a small program that combines the last two slides:

  1. Open scores.txt for reading.
  2. Check that the file opened, and print an error message if it did not.
  3. If it opened, read and print each name and score.

Test it by running the program without creating scores.txt. You should see the error message.

After students see the error, have them create scores.txt (or run the Writing To A File program first) and run again to see each name and score printed.

#include <fstream>
#include <iostream>
#include <string>
using namespace std;

int main() {
    ifstream inFile("scores.txt");

    if (!inFile.is_open()) {
        cerr << "Error: could not open scores.txt" << endl;
        return 1;
    }

    string name;
    int score;

    while (inFile >> name >> score) {
        cout << name << ": " << score << endl;
    }

    inFile.close();
    return 0;
}

Solution to the coding task. If the file opens, the loop reads each name and score until extraction fails, a preview of Reading From A File. With “Alice 95” and “Bob 87” in the file, the output is “Alice: 95” and “Bob: 87”. Full program: cpp/open_check.cpp

Where Is The File?

A file name is a path. There are two kinds:

  1. Absolute path: the full location, starting from the top of the drive.
  2. Relative path: a location measured from where the program is running.

Where Is The File? Absolute

An absolute path names every folder from the top of the drive.

ifstream macFile("/Users/alex/cisp360/scores.txt");
ifstream winFile("C:\\Users\\alex\\cisp360\\scores.txt");
  • It works no matter where the program runs.
  • It breaks when the program moves to another computer or folder.
  • On Windows, each \ in a string must be written as \\.

Where Is The File? Relative

  • "scores.txt" is a relative path.
  • It is resolved from the program’s working directory.
  • That may not be the same folder as the .cpp file.

When a file does not open, check both the file name and where the program is running.

Overwrite And Append

ofstream fresh("log.txt");
fresh << "Program started" << endl;
fresh.close();

ofstream later("log.txt", ios::app);
later << "Program ended" << endl;
later.close();
Mode Behavior
default output overwrite the file
ios::app add new data at the end

Reading From A File

#include <fstream>
#include <iostream>
using namespace std;

int main() {
    ifstream inFile("scores.txt");
    string name;
    int score;

    while (inFile >> name >> score) {
        cout << name << ": " << score << endl;
    }

    inFile.close();
    return 0;
}

The stream advances automatically as each value is read.

Design The File Before The Loop

Before writing the read loop, write down a small example file.

Alice 95
Bob 87
Carol 91

The example answers two questions: what does one record look like, and how does the reader know when to stop?

The File Format Is A Contract

  • The writer and reader must agree on the record shape.
  • They must also agree on the stopping rule.
  • A correct read loop matches the file’s contract.

Changing the file format means changing the code that reads it.

File Patterns

Every read loop needs a stopping rule. There are three common ones:

  1. Read until extraction fails: every remaining value is data.
  2. First value is a count: the file says how many records follow.
  3. Sentinel value: a special value marks the end of the data.

Separately, the file’s record shape decides how each record is read: with >> or with getline.

Pattern 1: Read Until Extraction Fails

int score;
vector<int> scores;

while (inFile >> score) {
    scores.push_back(score);
}

Use this when every remaining token in the file is data.

This is usually better than while (!inFile.eof()) because it tests the read itself.

Pattern 2: First Value Is A Count

3
Alice 95
Bob 87
Carol 91
int count;
inFile >> count;

for (int i = 0; i < count; i++) {
    inFile >> name >> score;
    cout << name << ": " << score << endl;
}

Use this when the file declares how many records follow.

Pattern 3: Sentinel Value Ends The Data

91
78
84
-1
int score;
inFile >> score;

while (score != -1) {
    scores.push_back(score);
    inFile >> score;
}

The sentinel must be a value that cannot be valid data.

Record Shape: Tokens Or Whole Lines

The stopping rule says when to stop. The record shape says how to read one record.

Mary Ann Lee
Bob Cruz
string line;

while (getline(inFile, line)) {
    if (line != "") {
        cout << line << endl;
    }
}

>> stops at spaces, so it can’t read “Mary Ann Lee” as one name. getline reads the whole line. The loop still stops like Pattern 1: when a read fails.

Not a fourth stopping rule. Any of the three stopping patterns can be combined with either record shape.

Choosing A Reading Pattern

File Design Loop Shape Disadvantage
all tokens are data read until extraction fails a bad value stops the loop early and looks like the end of the file
first value is record count counted for loop the count must match the records; a wrong count drops or misreads data
special value marks the end sentinel loop needs a value that can never be real data; a missing sentinel never ends the loop

Then choose the record shape: >> for space-separated fields, getline when a field may contain spaces.

Why Not eof() First?

while (!inFile.eof()) {
    inFile >> score;
    scores.push_back(score);
}

File scores.txt holds 91, 78, 84, each followed by a newline.

Pass eof() before read Read result scores
1 false 91 91
2 false 78 91 78
3 false 84 91 78 84
4 false (newline left) fails, score still 84 91 78 84 84

eof() becomes true only after a read fails, so the last value is stored twice. Test the extraction instead of predicting it.

Output verified: 91 78 84 84. If the file holds bad data (a word where a number belongs), the read fails without reaching the end, eof() never becomes true, and the loop never ends.

When Reading Stops Early

The same loop, while (inFile >> score), reads two different files:

File contents Values read Why the loop stopped
91 78 84 3 end of file: normal
91 seventy 84 1 seventy is not an int: format error

Both stop the loop the same way: the extraction fails. If the loop stops before all expected records are read, inspect the file format before changing the loop.

Using eof() After The Loop

while (inFile >> score) {
    scores.push_back(score);
}

if (inFile.eof()) {
    cout << "Read all " << scores.size() << " scores." << endl;
} else {
    cerr << "Error: bad data at value " << scores.size() + 1 << endl;
}

Before the loop, eof() is a guess. After the loop, it tells you why reading stopped.

Verified output. First file: “Read all 3 scores.” Second file: “Error: bad data at value 2”. This is the right job for eof(): diagnosing the stop, not controlling the loop.

Writing A Vector

vector<int> scores = {91, 78, 84, 95};
ofstream outFile("scores.txt");

for (int score : scores) {
    outFile << score << endl;
}

outFile.close();

One value per line is easy to write, easy to read, and easy to inspect.

Reading A Vector

vector<int> scores;
ifstream inFile("scores.txt");
int score;

while (inFile >> score) {
    scores.push_back(score);
}

inFile.close();

The vector grows as the file provides values.

Quick Consistency Test

  1. Build data in memory.
  2. Write the data to a file.
  3. Close the output stream.
  4. Open an input stream.
  5. Read the data back into memory.
  6. Compare what you read with what you wrote.

If the two match, the write format and the read loop agree. This is often called a round trip.

Writing Records As Text

ofstream outFile("students.txt");

outFile << "Alice " << 95 << endl;
outFile << "Bob " << 87 << endl;
outFile << "Carol " << 91 << endl;

outFile.close();

A record is one grouped unit of data. Here, each record has a name and a score.

Reading Records As Text

ifstream inFile("students.txt");
string name;
int score;

while (inFile >> name >> score) {
    cout << name << " earned " << score << endl;
}

inFile.close();

The extraction order must match the file’s field order.

CSV Files

ofstream outFile("students.csv");

outFile << "name,score" << endl;
outFile << "Alice,95" << endl;
outFile << "Bob,87" << endl;

outFile.close();

CSV files are plain text files with comma-separated fields. Spreadsheet programs can read them.

Common Practices

  • Check that every file opened before reading or writing.
  • Design the file format before designing the loop.
  • Match the loop pattern to the file’s stopping rule.
  • Keep text formats simple enough to inspect by eye.

Summary

  • File I/O is stream I/O connected to persistent storage.
  • The read loop must match the file’s format contract.
  • Clear file formats make programs easier to test and debug.

Assertions

What Should Never Be False?

A program adds a 5-point curve to every score. One student entered 98, and the input was validated.

  • The program doesn’t crash.
  • The report says the student earned 103 out of 100.
  • Every average that uses that score is wrong too.

How could the program catch a mistake like this the moment it happens?

Slides 37-56

Bug-first hook. Return to this exact bug on the invariants slide, where an assertion catches it.

Validation vs Assertion

Validation Assertion
Handles client mistakes Catches programmer mistakes
Gives a message and reprompts Stops the program during development
Part of normal behavior Documents an assumption

Use validation for data coming from outside the program.

What assert Does

  • assert checks a condition the programmer believes must be true.
  • If the condition is false, the program stops.
  • The failed condition points to a broken assumption.

Assertions turn assumptions into executable checks.

Basic assert Syntax

#include <cassert>

vector<int> scores = {91, 78, 84};
int size = scores.size();
int last = size;            // bug: should be size - 1

assert(last < size);
cout << scores[last] << endl;

The assertion fires before scores[last] reads past the end of the vector.

Without the assertion, scores[3] is undefined behavior: it may print garbage, crash, or appear to work. The assertion turns a silent bug into a loud one.

Assertions Express Preconditions

  • A precondition must be true before code runs safely.
  • A divisor should not be zero.
  • An index should be inside the valid range.

The assertion documents what the caller or earlier code must guarantee.

Asserting Inside A Function

#include <cassert>
#include <iostream>
using namespace std;

double divide(int numerator, int denominator);

int main() {
    cout << divide(10, 2) << endl;
    cout << divide(10, 0) << endl;
    return 0;
}

double divide(int numerator, int denominator) {
    assert(denominator != 0);
    return static_cast<double>(numerator) / denominator;
}

The first call prints 5. The second call breaks the precondition, and the program stops. This example intentionally omits input; user-entered denominators should be validated before the function call.

Reading An Assertion Failure

5
a.out: main.cpp:14: double divide(int, int): Assertion `denominator != 0' failed.
Aborted (core dumped)
Part Tells you
main.cpp:14 the file and line of the assertion
double divide(int, int) the function it was in
`denominator != 0' the assumption that was false

Don’t patch the assertion. Ask who passed a zero, and trace where the bad value came from.

Output from g++ on Linux, which most online compilers use. On a Mac the wording differs: Assertion failed: (denominator != 0), function divide, file main.cpp, line 14. Same three facts either way.

Adding A Message To An Assertion

double divide(int numerator, int denominator) {
    assert(denominator != 0 && "divide needs a nonzero denominator");
    return static_cast<double>(numerator) / denominator;
}
a.out: main.cpp:14: double divide(int, int): Assertion `denominator != 0 &&
"divide needs a nonzero denominator"' failed.
  • A string literal always counts as true, so && "message" never changes the result.
  • assert prints the whole condition, so the message appears in the failure.

Use the message to say what went wrong in plain words.

Verified with g++ -Wall: no warnings, and the output above (wrapped here to fit; it prints on one line). On a Mac: Assertion failed: (denominator != 0 && “divide needs a nonzero denominator”), function divide, file main.cpp, line 14.

Watch for the reversed mistake: assert(denominator != 0 || “message”) never fails, because the string is always true.

Which Assertion Stops The Program?

vector<int> scores = {91, 78, 84};
int total = 0;
for (int s : scores) {
    total += s;
}
int last = scores.size() - 1;

assert(total == 253);          // A
assert(scores.size() == 3);    // B
assert(scores[last] == 91);    // C
assert(last == 2);             // D

Predict before you run it.

Answer: C. total is 253 and size is 3, so A and B pass. scores[last] is 84, not 91, so C fires. D is true, but it never runs: the program stops at the first failed assertion.

Assertions Express Invariants

An invariant is a condition that should stay true while the program runs.

int score = 98;
int curve = 5;

score = score + curve;      // bug: forgot to cap at 100

assert(score >= 0 && score <= 100);

A valid score stays between 0 and 100, no matter how the program changes it. This assertion catches the bug from the start of the topic.

Verified output: Assertion `score >= 0 && score <= 100’ failed.

Point out that the next slide uses the same condition on client input, and there it is the wrong tool. Same condition, different source: the curve is the programmer’s code, the typed score is the client’s.

Do Not Use assert For Client Input

cin >> score;
assert(score >= 0 && score <= 100);

Bad client input is expected. Expected mistakes need validation and recovery.

Validation Handles Client Input

cout << "Enter a score from 0 to 100: ";

while (!(cin >> score) || score < 0 || score > 100) {
    cin.clear();
    cin.ignore(1000, '\n');
    cout << "Score must be 0 to 100. Try again: ";
}

Validation handles both a number out of range and a word typed instead of a number. It keeps the program running and tells the client how to recover.

Without cin.clear() and cin.ignore(), typing a word puts cin in a failed state and the loop never ends. Ties back to last lecture’s input validation.

Assertions Can Be Disabled

#define NDEBUG        // must come before the include
#include <cassert>
  • Defining NDEBUG removes every assert from the program.
  • Many release builds turn it on with the compiler flag -DNDEBUG.
  • Required behavior cannot depend on assert.

Assertions are development checks, not a substitute for program behavior.

Avoid Side Effects In Assertions

// Wrong: count only increases when assertions are on
assert(count++ < limit);

// Right: the work happens outside the assertion
count++;
assert(count <= limit);
  • Do not put assignments or increments inside assertion conditions.
  • Do not place required function calls inside an assertion.

The program should behave the same with or without NDEBUG.

Assertions And File I/O

if (!(inFile >> expectedCount) || expectedCount < 0) {
    cerr << "Error: bad record count" << endl;
    return 1;
}

for (int i = 0; i < expectedCount; i++) {
    if (!(inFile >> score)) {
        cerr << "Error: file ended early" << endl;
        return 1;
    }
    scores.push_back(score);
}

assert(static_cast<int>(scores.size()) == expectedCount);

The file is outside data, so every read is validated. The assertion checks only the program’s own work: each pass through the loop added exactly one score.

A short or corrupted file is a client problem, so it gets an error message, not an assertion. Once every read is validated, the loop either adds expectedCount scores or exits, so if the assertion ever fires, the bug is in this code, not in the file. Verified: a count of 3 with two scores prints “Error: file ended early”.

As written, nothing can make this assertion fire: the loop either adds exactly expectedCount scores or returns early. It guards against a future change. Suppose someone later skips out-of-range scores:

for (int i = 0; i < expectedCount; i++) {
    if (!(inFile >> score)) {
        cerr << "Error: file ended early" << endl;
        return 1;
    }
    if (score < 0 || score > 100) {
        continue;               // new: skip bad scores
    }
    scores.push_back(score);
}

assert(static_cast<int>(scores.size()) == expectedCount);   // now fires

A file with a score of 105 now yields fewer scores than the count promised, and the assertion fires. The programmer must decide: was skipping right (update the assertion), or is it a bug? Either way the mismatch is caught here instead of becoming a wrong average later. Invariants guard against code changes, not just today’s code.

Why the static_cast: it converts scores.size(), not the condition. size() returns size_t, an unsigned type; expectedCount is a signed int. Comparing signed with unsigned silently converts the int to unsigned, so a negative value would become a huge positive number, and g++ -Wall warns about it. Here expectedCount is already validated as nonnegative, so the comparison is safe; the cast removes the warning and shows both sides are compared as int. Alternative without a cast: int loaded = scores.size(); assert(loaded == expectedCount);

Coding Task

Write a function double average(const vector<int>& scores).

  1. Assert the precondition: the vector is not empty.
  2. Call it with three scores, then with an empty vector, and read the failure message.
  3. Add validation in main so the empty vector never reaches the function.

The point: the assertion documents the function’s assumption, and validation in the caller keeps the assumption true.

#include <cassert>
#include <iostream>
#include <vector>
using namespace std;

double average(const vector<int>& scores);

int main() {
    vector<int> scores = {91, 78, 84};
    vector<int> empty;

    cout << average(scores) << endl;

    if (empty.size() == 0) {
        cout << "No scores to average." << endl;
    } else {
        cout << average(empty) << endl;
    }

    return 0;
}

double average(const vector<int>& scores) {
    assert(scores.size() > 0);

    int total = 0;
    for (int score : scores) {
        total += score;
    }
    return static_cast<double>(total) / scores.size();
}

Solution to the coding task. Output: 84.3333, then “No scores to average.” Full program: cpp/average_assert.cpp

Common Practices

  • Assert programmer assumptions.
  • Assert preconditions before unsafe operations.
  • Assert invariants after state changes.
  • Validate client input and file data before trusting it.

Summary

  • Validate what can reasonably happen.
  • Assert what should never happen if the code is correct.

Key Takeaways

  • File I/O uses familiar stream operations, but the data persists beyond the program run.
  • A file’s format is a contract: record shape and stopping rule determine the read loop.
  • Use validation for expected bad input and assertions for programmer assumptions that should never be false.
