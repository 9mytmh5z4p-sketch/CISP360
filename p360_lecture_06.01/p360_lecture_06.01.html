Very Brief Review of Static

What Does Static Remember?

  • A static local variable is created once.
  • It keeps its value between function calls.
  • The name is still visible only inside that function.

Slides 4-7

Static Local Example

#include <iostream>
using namespace std;

void showCount();

int main() {
    showCount();
    showCount();
    showCount();
    return 0;
}

void showCount() {
    static int count = 0;
    count++;
    cout << count << endl;
}

Bridge to Patterns

  • static is a mechanism, not the main design idea.
  • It can make one stored value available through one controlled function.
  • Singleton uses that idea to describe a larger design choice.

Design Patterns

Why Name Solutions?

  • Programmers run into the same design problems again and again.
  • A shared name lets a team discuss the shape of a solution without redrawing it from scratch.

Slides 8-20

Christopher Alexander

  • Architect Christopher Alexander wrote about recurring design problems in buildings and towns.
  • His patterns described problems, forces, and reusable solution shapes.
  • The idea was not “copy this building”; it was “recognize this design situation.”

A Pattern Language

  • Alexander’s larger idea was a connected vocabulary of design choices.
  • Small patterns and large patterns could work together.
  • The value came from communication as much as construction.

From Buildings to Software

  • Software also has recurring design problems.
  • The exact code changes from program to program.
  • The design shape can still be recognized, discussed, and reused.

The Gang of Four Book

  • The Gang of Four book popularized software design patterns.
  • The authors are Erich Gamma, Richard Helm, Ralph Johnson, and John Vlissides.
  • They are often called the Gang of Four.

What Is a Design Pattern?

  • A design pattern is a reusable approach to a recurring design problem.
  • It names the problem, the structure, and the tradeoff.
  • The pattern is about intent, not memorized code.

What Patterns Are Not

  • Patterns are not syntax rules.
  • Patterns are not libraries.
  • Patterns are not guaranteed best practices.
  • Patterns are design vocabulary with consequences.

Pattern, Not Recipe

  • A recipe gives exact steps.
  • A pattern gives a shape that must be adapted to the program.
  • The same pattern may look different in small, medium, and large programs.

The Three Questions

  • What problem does this pattern solve?
  • What structure does it use?
  • What tradeoff does it introduce?

Common Practices

  • Start with the problem, not the pattern name.
  • Use the smallest structure that makes the design clearer.
  • Avoid adding pattern machinery when ordinary code is enough.

Pattern Categories

Summary

  • Design patterns name recurring design choices.
  • They help programmers recognize, explain, and maintain structure.
  • Every pattern also has a cost.

Singleton Pattern

Pattern Category

What If There Should Only Be One?

  • Some program resources should not have many independent copies.
  • A file name, counter, settings value, or shared output path may need one controlled access point.

Slides 21-31

Singleton Pattern

  • Singleton controls access so a program uses one shared resource.
  • The program reaches that resource through one function.
  • Other code asks for the shared resource instead of creating separate copies.

One Resource, One Access Point

Rule Meaning
one resource the program should not create several copies of the same resource
controlled access other code reaches the resource through one function
shared state callers see the same stored data

Example

The highlighted static local value is the controlled shared resource. The function is the access point.

Example 2

Use this slide to contrast the global-variable version with the static-local version. Both preserve shared state, but the global version exposes the state more broadly.

Why Static Shows Up Here

int& nextReportNumber() {
    static int reportNumber = 1000;
    return reportNumber;
}
  • The local static value is created once.
  • Each later call reaches the same stored value.
  • The value is kept inside the access function’s control.

When Singleton Is a Bad Fit

  • The data could be passed as a parameter.
  • The program may need multiple versions later.
  • The shared value changes in ways callers cannot easily see.

Common Practices

  • Use Singleton only when one shared resource is part of the problem.
  • Keep the shared resource small and focused.
  • Do not use Singleton as a disguised global variable.

Summary

  • Singleton controls access to one shared resource.
  • It is useful when the single-resource rule is intentional.
  • It should be chosen for a design reason, not convenience alone.

Menus and Functions

Who Owns Each Menu Job?

  • A menu program has repeated responsibilities.
  • Functions can keep each responsibility small.
  • main() should coordinate the pieces instead of doing every job itself.

Slides 32-51

Menu Program Responsibilities

  • Display the choices.
  • Read the user’s choice.
  • Process the selected action.
  • Repeat until the user chooses to quit.

Each responsibility can become a function or a small group of functions.

Display Menu Function

void displayMenu() {
    cout << "1. Deposit" << endl;
    cout << "2. Withdraw" << endl;
    cout << "3. Show balance" << endl;
    cout << "4. Quit" << endl;
}

This function owns the menu text.

Get Choice Function

int getChoice() {
    int choice;
    cout << "Choice: ";
    cin >> choice;
    return choice;
}

The function reads one value and returns it to the caller.

Action Functions

void showBalance(double balance) {
    cout << "Balance: $" << balance << endl;
}

An action function should do one menu job clearly.

Main as the Coordinator

int main() {
    double balance = 0.0;
    int choice;

    displayMenu();
    choice = getChoice();

    return 0;
}

main() owns the program flow and delegates details to helper functions.

Dispatching the Choice

if (choice == 1) {
    addDeposit(balance);
} else if (choice == 2) {
    makeWithdrawal(balance);
} else if (choice == 3) {
    showBalance(balance);
}

The dispatch code connects a user choice to the matching function call.

Menu Loop Shape

do {
    displayMenu();
    choice = getChoice();
    processChoice(choice, balance);
} while (choice != 4);

A menu loop keeps showing choices until the quit option is selected.

Reference Parameters in Menu Actions

void addDeposit(double& balance) {
    double amount;
    cout << "Deposit amount: ";
    cin >> amount;
    balance = balance + amount;
}

The reference parameter lets the action update the caller’s balance.

Default Parameters in Display Helpers

void printDivider(char symbol = '-', int length = 30);

Defaults keep common formatting calls short while still allowing customization.

    cout << "\nBanking Menu\n";
    cout << "1. Deposit\n";
    cout << "2. Withdraw\n";
    cout << "3. Show balance\n";
    cout << "4. Quit\n";
}

getMenuChoice()

int getMenuChoice() {
    int choice;

    cout << "Choice: ";

    while (!(cin >> choice) || choice < 1 || choice > 4) {
        cout << "Enter a menu choice from 1 through 4: ";
        cin.clear();
        cin.ignore(numeric_limits<streamsize>::max(), '\n');
    }

    return choice;
}

inputValidation

  • Check whether input extraction succeeded.
  • Check whether the value is within the allowed range.
  • Clear the failed state and discard the invalid input before trying again.

processChoice()

void processChoice(int choice, double& balance) {
    switch (choice) {
    case 1:
        addDeposit(balance);
        break;
    case 2:
        makeWithdrawal(balance);
        break;
    case 3:
        showBalance(balance);
        break;
    case 4:
        cout << "Goodbye.\n";
        break;
    default:
        cout << "Entered bad input" << endl;
    }
}

Various Choices

  • addDeposit() changes the balance through a reference parameter.
  • makeWithdrawal() checks the balance before changing it.
  • showBalance() reads the balance without changing it.

Summary

  • Menus stay manageable when each function owns one responsibility.
  • Reference parameters let menu actions update caller-owned state.
  • Default parameters can simplify repeated display helper calls.

Key Takeaways

  • Design patterns name recurring design choices.
  • Static local storage can support a larger design rule, but it is not the design itself.
  • Singleton controls access to one shared resource.
  • Menu programs become clearer when display, input, dispatch, and actions have separate functions.

Very Brief Review of Static: Good Practices

  • Use static local variables when a function intentionally needs memory between calls.
  • Keep the remembered state small and easy to explain.
  • Prefer visible parameters and return values when state does not need to persist.

Very Brief Review of Static: Common Mistakes

  • Treating static as a shortcut for avoiding parameters.
  • Forgetting that previous calls affect the next call.
  • Assuming local scope means short lifetime.

Very Brief Review of Static: More Examples

int nextId() {
    static int id = 1000;
    id++;
    return id;
}

Each call returns a new value because id keeps its previous value.
